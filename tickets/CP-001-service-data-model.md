# CP-001: Design Service Data Model

## Goal

Define the information HEARTBEAT must store about each monitored service.

## Related Requirements

- REQ-001
- REQ-002
- REQ-003
- REQ-004
- REQ-005

## Questions to Resolve

- What information must HEARTBEAT store about a service?
- Which service fields should be editable?
- Which fields should HEARTBEAT control internally?
- How should HEARTBEAT determine how a service is monitored?
- What validation should occur before a service is accepted?

## Proposed Fields

- id
- name
- url
- check_type

Potential future field:

- enabled

## Validation Rules

- id must be generated by HEARTBEAT.
- id must be unique.
- id must not be editable.
- name is required and cannot be empty.
- url is required and must have a valid URL structure.
- check_type is required and must match a supported HEARTBEAT check type.
- name, url, and check_type may be modified by an authorized administrator.

## Decisions

- HEARTBEAT will generate service identifiers rather than allowing administrators to manually assign them.
- Service identity will remain separate from its display name so a service can be renamed without changing its identity.
- check_type describes how HEARTBEAT monitors a service.
- Monitoring results such as response time, HTTP status, and availability do not belong directly to the Service model. They will belong to a future health-check model.
- Service configuration should eventually be verified against its monitoring method before active monitoring begins.
- An enabled field would be useful for temporarily disabling monitoring without deleting a service, but it is not required for v0.1.
